# Правила составления промптов для Cline (DeepSeek V4)

Правила координации: docs/COORDINATION-RULES.md.

## Модель и effort (фиксация 2026-09-10; changelog DeepSeek 2026-09-10)
- V4.1 Flash выпущен 2026-09-10 (имя deepseek-flash); deepseek-v4-flash и deepseek-v4-pro роутятся на V4.1 Flash; с 2026-09-14 12:00 Beijing pro выведен (роутинг на Flash по цене Flash).
- V4.1 Flash превосходит V4 Pro по всем метрикам (performance, cost, speed, total time). ПРАВИЛО: pro в промптах не используется, напоминаний не требуется.
- Модель в промптах кодеру: всегда deepseek-flash (в DSH UI — DeepSeek-V4-Flash). Сложность регулируется ТОЛЬКО effort из шкалы DSH: Off | Low | High | Max (medium отсутствует): Off для кода не используется; Low — механические шаги; High — ежедневные фиксы/агент (по умолчанию); Max — сложная отладка и архитектура.
- Если задача решается на low effort — не поднимай effort.
- Цены Flash с 2026-09-10 12:00 Beijing: off-peak $0.003/M cache-hit, $0.15/M cache-miss input, $0.6/M output; peak x2; тяжёлые прогоны планировать в off-peak.

## Экономия токенов
1. Модель и effort: обоснование выбора одной строкой перед промптом.
2. Контекст: если задача помещается в ≤10 ходов текущего чата и не имеет повторяющихся ошибок — продолжай в той же задаче, не создавай новую. Новая задача — только если контекст загрязнён (≥2 отвлечённых ветки или ≥2 ошибки с повторными правками). При переносе — компактное резюме ≤10 строк.
3. Гигиена данных: не запрашивай полные логи/файлы >500 строк; используй выдержки, grep, диапазоны строк. Фикстуры >100 КБ — читать точечно (начало/конец/ключи).
4. Формат ответа кодера: diff вместо целых файлов; отчёт ≤10 строк; не повторять текст задачи в ответе.
5. Контекст передачи: в начале каждого промпта кодеру ОБЯЗАТЕЛЬНО указывать две строки: «Ветка: новая | текущая» и «Чат: новый | прежний (контекст переносится)». Это предотвращает путаницу между параллельными задачами и определяет необходимость блока «Контекст-перенос».

## Регрессионный контур (обязателен в каждой задаче)
1. Полные файлы целиком в ответе.
2. Явный список «НЕ трогать» + тест, что эти пути не изменились.
3. «Готово» принимается только с цитатами: npm test + реальный прогон на двух разных чатах (холодный + SPA). Отчёт без этих цитат — не принимается.

Для сложных задач — сначала plan mode: архитектура и риски, затем реализация.

## Сессии DSH — семантика для промптов (фиксация 2026-09-13)
- **НОВАЯ сессия** = задача выполняется в новой сессии, которую пользователь создаёт в GUI DSH (кнопка «New Session») перед вставкой промпта. В промптах писать: `DSH: workspace ai-context-monitor-clean → работать в НОВОЙ сессии с именем «X»`.
- **ТЕКУЩАЯ сессия** = продолжить работу в уже идущей сессии (упоминать только когда явно нужно продолжение; в промптах по умолчанию — никогда).
- Кодер DSH не умеет создавать сессии инструментами (HTTP 403); создание — только из GUI. Если создание нового чата нужно — пользователь создаёт сам.
- Правило применяется ко всем промптам по умолчанию, кроме случаев явного продолжения.

## Правила формирования промптов для DSH (v2)

### Структура каждого промпта
1. **РОЛЬ** — конкретная роль для задачи (Senior DevOps, Senior Chrome Extension Engineer, и т.д.)
- РОЛЬ обязательна для всех промптов без исключений. Пропуск этой строки считается нарушением стандарта.
2. **ИСТОЧНИК ИСТИНЫ** — ссылка на PROJECT_HANDOFF.md + актуальный коммит
3. **ЗАДАЧА** — одна строка, что делаем
4. **ШАГИ** — нумерованный список (ШАГ 1, ШАГ 2, ...) с атомарными действиями
5. **ТРЕБОВАНИЯ** — технические ограничения
6. **ОГРАНИЧЕНИЯ** — что НЕ делать
7. **КРИТЕРИИ ПРИЁМКИ** — таблица с результатом
8. **ВЫХОД** — файлы, коммит, чеклист

### Мета-правила
- Каждый промпт = одна фаза/шаг, не смешивать
- Указывать reasoning effort (off/low/high/max) с обоснованием
- Указывать, в какую сессию копировать (новую или текущую) с обоснованием
- Если задача требует участия владельца (runtime-валидация, удаление файлов) — выносить в отдельный блок "Задача владельца"
- После формулирования промпта — краткое резюме для владельца (что сделать, что сообщить)
- При старте новой фазы/шага декомпозиции — обязательно формировать аппендикс статуса в PROJECT_HANDOFF.md и заполнять docs/ACCEPTANCE-TEMPLATE.md до начала реализации.


## SHA и точность цифр (Post-Mortem 2026-11-11)
- Всегда указывать SHA из вывода `git log -1`, а не из памяти координатора. При расхождении — приоритет у вывода терминала.
- В промптах запрещены метафоры в оценке кода («90% функций»). Только точные цифры из замеров (Cloc, Coverage).
- Перед живой приёмкой в промпт включать `node build.mjs` и «Обновить расширение в chrome://extensions»; тестируется сборка из актуального `dist`, не из `Downloads`.
- В каждый промпт DSH добавлять строку: `НЕ создавай аппендикс и не меняй документацию, пока координатор явно не попросит`.

## Гигиена верхнего блока handoff (фиксация 2026-10-11)

Прецеденты: v57/v59/v60/v61 — четыре подряд случая, когда верхний блок `PROJECT_HANDOFF.md` требовал отдельного третьего docs-коммита после push.

**Правило.** Верхний блок (строка 5: `HEAD → <SHA>, origin/main = <SHA>, ahead = N`) отражает **пост-push** состояние.

1. В двухшаговом паттерне docs-синка (аппендикс → SHA-синк) верхний блок НЕ трогается: ни в первом, ни во втором коммите (оба ещё не запушены).
2. После push — третий docs-коммит: `docs(handoff): sync top block HEAD → <SHA>, ahead = 0`. Значения: `HEAD` == `origin/main` == SHA предыдущего коммита (перед самим sync-коммитом), `ahead = 0`. Совпадения SHA в верхнем блоке с реальным `git log -1` не требуется: sync-коммит намеренно отстаёт на один коммит, потому что не может содержать свой собственный SHA.
3. **Запрещено** ставить в верхний блок значение, устаревающее в момент собственного коммита (например, `ahead = 3` при двух незапушенных: значение верно только до push).

**Проверка:** после push `git rev-list --count origin/main..HEAD` = 0 И в строке 5 `HEAD == origin/main` И `ahead = 0`.

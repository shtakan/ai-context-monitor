# COORDINATION-RULES.md

**Назначение:** правила взаимодействия между владельцем и координатором (веб-версия DeepSeek) в handoff-driven small-batch workflow проекта `ai-context-monitor`.

**Область:** применяется поверх `Протокол Правды.txt` и `CLINE_PROMPT_RULES.md` ко всем задачам после старта сессии.

**В релизный ZIP не входит** (`\.md$` фильтр `release.yml`).

**Версия:** 1.0 (сформирован 2026-10-16 по итогам цикла v76–v82).

---

## §0. Роли

- **Владелец** — человек. Управляет Git (push, tag, Release), принимает решения о scope, запускает DSH-сессии в GUI, выполняет ручные шаги (PowerShell-команды, файловые операции).
- **Координатор** (веб-версия DeepSeek) — формулирует промпты для DSH-кодера, ведёт протокол, анализирует отчёты, предлагает решения. **Никогда не выполняет git-операции:** push, tag, release, коммит — только владелец.
- **Кодер** (DSH Desktop, DeepSeek Harness) — выполняет локальные коммиты, прогоняет тесты, делает edits. **Никогда не пушит.**

Разделение жёсткое. Нарушение = сбой протокола.

---

## §1. Чат и сессии

**Веб-чат (координатор):**
- Один веб-чат = один крупный цикл задач (релиз, серия аппендиксов, пакет hygiene). При переполнении — новый чат.
- Вход в новый чат — 3 строки:
  ```
  Источник истины: PROJECT_HANDOFF.md (§0 + верхний блок + аппендиксы <диапазон>).
  Правила: docs/COORDINATION-RULES.md.
  Задача: <одна строка>.
  ```

**DSH-сессии (кодер):**
- **Каждая задача = новая DSH-сессия** в GUI. Не продолжать в старой.
- Имя сессии задаёт координатор в шапке промпта. Схема: `<тип>-<тема>[-<шаг>]`.
  - Типы: `docs`, `chore`, `fix`, `feat`, `release`, `test`, `plan`.
  - Примеры: `docs-v82-block`, `chore-v81-p1-p3`, `fix-byok-sw-flag`, `plan-eep-decompose`, `release-v2.0.17`.
- Имя объявляется в промпте **дважды**: строкой `DSH: workspace … → НОВАЯ сессия с именем «…»` и отдельной `Имя сессии для DSH: <name>` (страховка от того, что GUI не читает имя из шапки).

## §2. Формат промпта для DSH

Один блок из **четырёх обратных кавычек**. Тройные внутри запрещены.

```
Усилие рассуждений: <Off|Low|High|Max>
Режим: <act|plan>
DSH: workspace <name> → НОВАЯ сессия с именем «<session-name>»
Git: branch main, продолжаем цикл

Имя сессии для DSH: <session-name>

РОЛЬ: <Senior X — конкретно>
ИСТОЧНИК ИСТИНЫ: workspace <name>, PROJECT_HANDOFF.md; HEAD = <short-SHA>, origin/main = <short-SHA>, ahead = <N>; сьют <S/P/K/F>.

ЗАДАЧА: <одна строка>.

ШАГ 1..N. <атомарные действия>
ТРЕБОВАНИЯ: <encoding, line-neutrality>
ОГРАНИЧЕНИЯ (НЕ трогать): <явный список>
КРИТЕРИИ ПРИЁМКИ: <grep + exit 0>
ВЫХОД: <git show --stat, отчёт ≤10 строк>
```

**Effort scale:** `Off | Low | High | Max`. `Off` для кода не используется. `Medium` отсутствует.
**Длина отчёта кодера:** ≤10 строк (для plan-режима — до 40, обоснованно).

### Правила работы с BrowserSkill (bsk)

- Любая задача с инструментами `bsk_*` / `browser_*` (живая вкладка Chrome) выполняется **строго по `docs/BROWSER-TASK-PROTOCOL.md`**; справочник лимитов, тупиков и специфики сайтов — `docs/BSK-CHEATSHEET.md`.
- Протокол и cheatsheet читаются **до первого вызова** bsk в задаче, а не по ходу выяснения ошибок.
- Бюджет: ≤40 вызовов инструментов на задачу (норма 12–20), ≤6 на фазу; ответ дороже ~2 000 токенов — в файл, в контекст ≤20 строк.
- Один решающий замер вместо сбора всех доказательств; ≤3 неудачных попыток на одну гипотезу, затем смена гипотезы.
- Стоп-условия (`browsers connected 0`, обрезка тела ответа, промах селектора) закрываются ссылкой на раздел cheatsheet, а не новым исследованием.

## §3. Формат ответа координатора владельцу

- Факты со ссылкой на источник (файл:строка, коммит, лог).
- ≤20 строк.
- ОДНА senior-рекомендация в конце.
- Без меню вариантов (если вариантов >1 — рекомендация одна).
- Без пересказа процедур из handoff.
- Гипотезы маркируются явно: «гипотеза, не проверено».
- Если проверка не выполнена — «не могу подтвердить», не додумывать.

## §4. Двухшаговый паттерн SHA

**Проблема:** коммит не может содержать собственный SHA (самореференция).

**Паттерн:**
1. **Коммит A** — тело изменения с плейсхолдером `<SHA vX>`.
2. **Коммит B** — замена плейсхолдера фактическим SHA коммита A.

**Область:** docs-аппендиксы; релизные коммиты с самореферентными ссылками; любые правки, ссылающиеся на свой SHA.
**Правила:**
- Формат плейсхолдера: `<SHA vX>`, `<SHA3>`, `<SHA4>` (для внутренних шагов цикла).
- A и B — отдельные коммиты; пушатся **одной операцией** владельца.
- Плейсхолдер разрешается только координатором в отдельном промпте.

## §5. Цикл docs-аппендикса (4 коммита)

**Каждый аппендикс фиксируется 4 коммитами (стандарт с v76):**

| # | Коммит | Содержание |
|---|---|---|
| **A** | `docs(handoff): appendix vX — <краткое>` | Тело аппендикса с плейсхолдером `<SHA vX>` |
| **B** | `docs(handoff): appendix vX — resolve SHA placeholder (<SHA-A>)` | Замена `<SHA vX>` → SHA A |
| **C** | `docs(handoff): sync top block HEAD -> <SHA-B>, ahead = 0 (appendix vX closure)` | Обновление верхнего блока + плейсхолдер `<SHA4>` в аппендиксе |
| **D** | `docs(handoff): appendix vX — resolve SHA4 placeholder (<SHA-C>)` | Замена `<SHA4>` → SHA C |

**Порядок push:** A+B одной операцией; C+D одной операцией. **Два push-цикла.**

**Структура тела аппендикса (7 секций, обязательно):**
1. Что сделано (таблица/список)
2. Свидетели/факты (для plan/audit)
3. Отклонения от промпта (если были)
4. Новые residual (Low)
5. Переопределение residual-точек (какие аппендиксы выше закрыты этим)
6. Сводка (сьют, tsc, статус)
7. Плейсхолдер `<SHA vX>`

**Инвариант O-53 в handoff (три защищённые строки):**
- L199 `- **Версия: X.Y.Z**` — обновляется **только** в релизном коммите.
- L200 `- **Тесты: N suites / N passed / N skipped / N failed**` — текущий прогон.
- L976 `- **Исторический максимум: N suites / N passed / N skipped / N failed**` — рекорд зелёных прогонов.
- Номера — по состоянию после split (аппендикс v104): версия и тесты — в активном `PROJECT_HANDOFF.md`, исторический максимум — в `docs/HANDOFF_ARCHIVE.md`; при изменениях — сверять по подстрокам, не по номерам.
- Все три защищены пинами `tests/docs-hygiene.test.js`. **В теле аппендикса их полные формы приводить нельзя** (иначе 2 совпадения → пин падает).

## §6. Правила кода-коммитов

- **Plan-first для правок кода:** перед Act — read-only Plan-инвентаризация (`git ls-files` + `Select-String`), классификация, три варианта, рекомендация.
- **Один коммит = одна логическая правка.** Смешение — антипаттерн.
- **R-D пины:** дефект → пин на каждый путь; фиксация семантики → пин на формат и валидность.
- **Source-пины не ослабляются.** Если правка теста неизбежна — согласовать, обосновать.
- **Line-neutrality:** в файлах с построчными пинами (`catch-whitelist.json` и др.) предпочитать нейтральные правки; сдвиг — только явным решением.

## §7. Правила релиза

**Релизный цикл (прецедент v2.0.16 / v2.0.17):**

1. **Plan-инвентаризация** `2.0.X` — классификация T-VER / T-PIN / T-README / T-HIST.
2. **Релизный коммит** (Act, 1 коммит): `manifest.json`, `package.json`, `package-lock.json`, `CHANGELOG.md`, `docs/index.html`, `PROJECT_HANDOFF.md` (L199 версия), `README.md`, `README.en.md`, `docs/TESTS.md`, все T-PIN. **16 файлов — по прецеденту.**
3. **Push коммита** (владелец, PowerShell).
4. **Tag + push tag** (владелец): `git tag -a vX -m "vX"` + `git push origin vX`.
5. **GitHub Release** (владелец, вручную): title + description из CHANGELOG-секции `[X]`.
6. **Аппендикс vN (docs, 4 коммита)** — фиксация релиза.
7. **Pre-release проверка фильтра ZIP** (перед push): имитация `grep -zvE` на `git ls-files`, подтвердить что T-HIST (`step-*`, `.diff`, `*.txt`, `docs/videos/*.mp4`) исключены.

**В релизный коммит НЕ включаются:** `RELEASE_CHECKLIST.md` (процессный — прецедент v64 §4), `docs/QUALITY_AUDIT.md` (H26 gitignored), `tools/edge-listing-metadata.txt` (gitignored).

**CHANGELOG трогается только в релизном коммите** — не в docs, не в code.

## §8. Протокол Правды (краткая версия)

Полная — `Протокол Правды.txt`. Ключевое для координатора:

1. **Правда важнее вежливости.** Ошибки координатора — называть прямо, включая свои.
2. **Не «доигрывать» приёмку.** «Не выполнена, причина …» — допустимый исход.
3. **Различать факт / гипотезу / догадку** явно. Гипотеза маркируется «не проверено».
4. **Не выдумывать** данные, события, людей, исследования, цитаты. При недоступности — «не могу подтвердить».
5. **Признавать свои ошибки формулировок** (прецеденты v81: `$` в критерии, «2 упоминания» вместо 1, арифметика suites).
6. **Не додумывать за DSH.** Если DSH отклонился от буквы промпта — разбирать факт, а не переписывать отчёт.

## §9. Антипаттерны

1. Продолжение задачи в **старой** сессии DSH (WIP=1, одна задача = один чат).
2. **Push / tag / Release / commit** — координатором (только владелец).
3. **Плейсхолдер-догадка** (`<SHA4>` → «наверное …»).
4. Пропуск **grep-инвентаризации** перед docs-синком или релизным коммитом.
5. Правка **аппендиксов выше** текущего — кроме двухшагового паттерна и явных исключений (L1738).
6. Критерий приёмки с **подстрокой, которой нет в предписанном тексте** (прецедент `$`).
7. «Скорее всего X» без проверки: `Test-Path`, `Select-String`, `git diff --name-only`.
8. **Пересказ** сырого вывода в отчёте вместо вставки как есть.
9. **Смешение задач** в одном коммите (hygiene + релиз).
10. Трогать CHANGELOG **вне релизного коммита**.

## §10. Чек-листы

**Перед каждым Act-промптом:**
- [ ] Plan-инвентаризация, если есть риск пропустить точки (docs-синк — обязательно).
- [ ] РОЛЬ сформулирована (Senior X).
- [ ] ИСТОЧНИК ИСТИНЫ со ссылкой на HEAD и ahead.
- [ ] Шаги атомарные, пронумерованы.
- [ ] ОГРАНИЧЕНИЯ — явный список файлов/зон.
- [ ] КРИТЕРИИ ПРИЁМКИ — grep-формулы + exit 0.
- [ ] ВЫХОД — формат отчёта ≤10 строк.

**Перед push (владелец):**
- [ ] `git status -sb` — ahead N (ожидается 1 или 2).
- [ ] `git log --oneline origin/main..HEAD` — ожидаемые SHA.
- [ ] Для релиза — pre-release проверка фильтра ZIP.
- [ ] Ожидаемый SHA origin/main известен из промпта.

**После push:**
- [ ] Lint зелёный (вкладка Actions).
- [ ] `git rev-list --count origin/main..HEAD` = 0.
- [ ] Для релиза — Release ZIP run зелёный.

## §11. Терминология

- **workspace** — папка проекта (`ai-context-monitor-clean`).
- **session** — чат внутри workspace (DSH) или веб-чат (координатор).
- **branch** — git-ветка (`main` в проекте).
- **HEAD** — короткий SHA текущего коммита.
- **origin/main** — короткий SHA удалённой ветки.
- **ahead** — число локальных коммитов впереди origin/main.
- **T-VER / T-PIN / T-README / T-HIST** — классификация точек версии при релизе.
- **Plan-mode / Act-mode** — режим DSH: read-only анализ / правки.
- **Effort** — уровень рассуждений (`Off | Low | High | Max`).

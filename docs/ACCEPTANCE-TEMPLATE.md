## 1. Зачем шаблон

Живая приёмка — единственный вид доказательства, который проект признаёт для live-багов
(конвенция процесса 4: «Харнесс ≠ приёмка live-багов»). Затруднения в приёмке почти всегда не
технические, а постановочные: в промпте не задана одна из пяти осей — **граница автоматизации,
предусловия, критерий в числах, точка артефакта, формат отчёта**. Агент достраивает недостающее
догадкой, и появляется либо «приёмка по скриншоту», либо файл, который искали не в той папке,
либо вывод «экспорт работает» без проверки самого критерия.

## 2. Пять осей (обязательный минимум в промпте)

| Ось | Что должно быть в промпте | Какой отказ это закрывает |
|---|---|---|
| Граница автоматизации | что агент делает сам (навигация, ожидание, консоль, сеть, инспекция файла) и что физически не может (UI другого расширения, `chrome-extension://<id>/…`) → это шаг владельца через `browser_assist request-help` с таймаутом | попытки кликать чужой `chrome-extension://` и «пустой» `observe` вместо запроса владельцу |
| Предусловия | проверка инструмента ДО старта (`bsk doctor`, версия CLI/плагина), фактические значения настроек, где окажется артефакт | `unrecognized subcommand 'request'` (CLI 0.3.0 против плагина 0.3.1); поиск файла не в той папке |
| Критерий в числах | boolean-формула: файл существует, размер/строки, счётчики совпадений в файле = счётчику из консоли | вывод «экспорт есть» вместо «reasoning доехал до файла» |
| Точка артефакта | абсолютный путь папки загрузок (в этом окружении `C:\Users\oleg\Desktop`: `Preferences.savefile.default_directory`, а НЕ `Downloads`) и маска имени | файлы 2026-09-20 «не нашлись»: искали в `%USERPROFILE%\Downloads` |
| Отчёт и честность | формат отчёта (diff + ≤10 строк), отдельный коммит на handoff, разрешённый исход «приёмка не выполнена», перечень непроверенного | выдуманные результаты и молчаливая подмена пути |

## 3. Шаблон промпта (копировать целиком и подставить `<…>`)

```text
Живая приёмка <ID>: <название>.
Цель: получить <артефакт> и доказать <критерий в числах>.

1) Предусловия — проверь ДО старта и доложи, что видишь:
   - инструмент: <bsk doctor / версия CLI и плагина>; если ошибка версий или демона —
     сначала почини инструмент, доложи починку; приёмку не имитируй и не подменяй
     похожим прогоном;
   - состояние настроек: <ключ> = <значение> — назови ФАКТИЧЕСКИЕ значения перед прогоном;
   - где окажется артефакт: <абсолютная папка загрузок, не «Downloads по умолчанию»>.

2) Границы автоматизации:
   - делаешь сам: <навигация, ожидание SPA/XHR, чтение консоли, инспекция файла>;
   - физически не можешь: <UI другого расширения chrome-extension://… и т.п.> — это шаг
     владельца, запроси его через browser_assist request-help с таймаутом;
   - обходить границу самодельным путём запрещено. Если видишь легальную замену —
     предложи её и дождись «да».

3) Сценарий: <шаги переходами/кнопками>.
   Разрешённая замена пути: <например, автоэкспорт по порогу>; если пользуешься ею —
   скажи прямо и укажи, какие точки кода общие с основным путём.

4) Критерий приёмки — boolean-формула, не впечатление:
   - файл <маска> существует в <папка>, размер > <N> байт, строк > <M>;
   - в файле <маркер A> = <маркер B> = <N> и равно <счётчику из консоли>;
   - в консоли есть свидетели: <4–6 конкретных строк с корреляцией по <convId>>;
   - настройки после прогона те же, что до.

5) Доказательства в отчёте: (а) точный путь и размер файла; (б) 4–6 строк консоли;
   (в) команды, которыми проверил файл (не «я посмотрел»).

6) Честность: приёмка НЕ считается выполненной по «скачалось», по скриншоту без файла
   и по прошлому прогону. Не смог — напиши «приёмка не выполнена, причина …».
   Что не проверено живьём (например, MD при fmt=txt) — перечисли отдельно.

7) Отчёт: diff + ≤10 строк, статус. Правки handoff — отдельным шагом/коммитом
   (двухшаговый паттерн SHA, конвенция 7). Настройки владельца сверх перечисленных
   не трогай; в конце приведи их к исходным.
```

## 4. Критерий приёмки — как формулировать

Критерий обязан быть проверяемым без памяти и без эталона «в голове» владельца
(урок процесса: владельцу НЕ давать задания «сравнить побайтово с прежним»). Годные формы:

- счётчики совпадений: `<маркер>` в файле = N, и то же N в консоли (`reasonings=53`);
- маркеры-свидетели: конкретная строка лога с `convId` и вердиктом (`hidden=on branch=includeHiddenExportBlocks`,
  `txt-roles … kept=105 dropped-containers=0`, `download trigger=autoexport file=…`);
- инварианты: `[REASONING]` = `[ANSWER]` = `reasonings`; `msgsIn` = `msgsOut` = `kept`;
- «до/после»: настройки и база байтово/структурно прежние вне затронутого пути.

Плохо: «убедиться, что reasoning экспортируется». Хорошо: «`[REASONING]` = `[ANSWER]` = число
`reasonings=` из консоли, и это число одинаково в двух независимых источниках (файл и лог)».

## 5. Анти-паттерны (что приводит к затруднениям)

1. «Проверь, что всё работает» / «сделай приёмку O-XX» без критерия — критерий придумает агент, и он будет мягче нужного.
2. «Экспорт текста» без режима (тумблер) и без папки — результат окажется штатно пустым (или не там).
3. Смешение двух критериев (TXT и MD) в одном прогоне, когда генератор даёт только один формат.
   Правильно: один критерий — один прогон; второй критерий либо отдельным прогоном, либо явно «закрыт пинами», либо честно «не проверен живьём».
4. Отсутствие разрешённого шага владельца → агент ищет обход запретной границы (и тратит прогон).
5. Нет предусловия про инструмент → ошибка версий CLI принимается за «инструмент сломан».
6. Нет запрета на «приёмка по памяти/прошлому прогону» → в отчёт попадает файл, которого нет на диске.
7. Нет требования назвать фактические значения настроек → дефолт (тумблер OFF, например) читается как дефект.

## 6. Легальные исходы приёмки

- **пройдена** — критерий выполнен, доказательства в отчёте;
- **пройдена с границей** — критерий выполнен по одному пути, другой путь явно назван непроверенным
  (живой образец: TXT проверен живым прогоном, MD закрыт пинами и ручным путём попапа);
- **не выполнена** — с причиной; это нормальный результат, а не провал сессии;
- **заблокирована средой** — с названной границей (например, UI чужого расширения не скриптится),
  и с указанием, какой ручной шаг владельца разблокирует приёмку.

## 7. Мини-чеклист перед отправкой промпта

- [ ] названа граница «агент / владелец» и механизм шага владельца (`request-help` + таймаут);
- [ ] есть предусловие «сначала проверь инструмент, назови версии»;
- [ ] названы фактические значения настроек, влияющих на критерий;
- [ ] указан абсолютный путь папки загрузок и маска имени файла;
- [ ] критерий — формула с числами, а не прилагательное;
- [ ] перечислены ожидаемые строки-свидетели консоли и `convId` для корреляции;
- [ ] сказано, что «приёмка не выполнена» — допустимый результат;
- [ ] задан формат отчёта и правило отдельного коммита на handoff.


## 8. Чеклист прохождения живой приёмки

**Правило:** каждый пункт имеет бинарный вердикт (`ок` / `не ок`) и свидетеля — что именно видели.
Пункт без свидетеля считается непроверенным. Чеклист заполняет владелец в браузере; агент ведёт
протокол и не подменяет наблюдение выводом.

**A. Предусловия (до старта)**
- [ ] расширение загружено, версия на карточке = версии в `manifest.json`;
- [ ] в дереве расширения нет файлов/папок с ведущим `_` кроме `_locales` (иначе плавающий отказ загрузки);
- [ ] консоль расширения открыта, фильтр сброшен;
- [ ] названы фактические значения настроек, влияющих на критерий.

**B. Сценарий (по шагам)**
- [ ] шаг 1: <действие> → наблюдаемый результат: <что видно>;
- [ ] шаг N: <действие> → наблюдаемый результат: <что видно>.

**C. Критерий (формула, не впечатление)**
- [ ] `<маркер A>` = `<маркер B>` = `N`, и то же `N` в консоли;
- [ ] настройки после прогона те же, что до.

**D. Границы**
- [ ] названо, что проверено живьём;
- [ ] названо, что закрыто пинами и живьём НЕ проверялось;
- [ ] названо, что заблокировано средой и каким шагом владельца разблокируется.

**E. Закрытие**
- [ ] вердикт: пройдена / пройдена с границей / не выполнена / заблокирована;
- [ ] запись в `PROJECT_HANDOFF.md` отдельным коммитом (двухшаговый паттерн SHA).

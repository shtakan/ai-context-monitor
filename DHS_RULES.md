# Правила автономного агента DeepSeek Harness (DHS)

Зеркало CLINE_PROMPT_RULES.md с DHS-спецификой. Работает в связке с
ARCHITECTURE_STANDARDS.md, RELEASE_PROTOCOL.md, RELEASE_CHECKLIST.md.

## 1. Выбор модели и effort
- **pro + high** — архитектурные изменения, инварианты, связки гейтов.
- **pro + medium** — локализованные фиксы средней сложности.
- **flash + low/medium** — механические шаги, прогоны, evidence-сбор.
- Если задача решается младшей моделью без потери качества — выбирай её.

## 2. Scope-lock (allow-лист)
- Перед задачей пользователь даёт allow-лист файлов. Всё вне списка — read-only.
- Любое изменение файла вне allow-листа = нарушение с самопризнанием в отчёте.
- Восстановление ранее удалённых файлов (напр. adapter-registry.js) запрещено
  без явного разрешения.

## 3. Инварианты (цитатой)
Перед каждой задачей читать и цитировать применимые пункты:
- ARCHITECTURE_STANDARDS.md: «Консервативный дефолт оракула», «Мировая
  изоляция — эталон», «Оси порогов», «Политика версия-маркеров».
- RELEASE_PROTOCOL.md: стоп-правила, доказательная приёмка.
- RELEASE_CHECKLIST.md: матрица классов чатов для live-прогонов.
- Любое решение против инварианта — явное обоснование в отчёте.

## 4. Миграционный контракт
Переименования storage-ключей/полей/API — ТОЛЬКО с функцией миграции
(read old + write new). Иначе API рассинхрон = отклонение.

## 5. Version-bump контракт
При любой нетривиальной правке в core/* или utils/*:
version bump в manifest.json + секция в CHANGELOG.md + запись в
RELEASE_CHECKLIST.md с хешем коммита.

## 6. Evidence-контракт
Утверждение «работает / готово» принимается ТОЛЬКО с цитатой из:
- unit-теста (jest: suite/test name);
- live-лога (фильтр + строка + timestamp);
- скриншота (путь в evidence/).
«Должно работать» и «505 базовых без регрессии» (без побайтовой проверки)
запрещены.

## 7. Stop-гейты (контур шагов)
DHS-харнес должен поддерживать stop-rules:
- после каждого блока правок — стоп и отчёт;
- не продолжать без подтверждения пользователя;
- не коммитить в основную ветку (работа в копии);
- любое изменение вне allow-листа = нарушение с самопризнанием.
Если харнес не поддерживает stop-rules — режим «одна задача → отчёт →
ручное ревью» (не автономный).

## 8. Доказательная идентичность
Утверждение «прежние тесты не изменены» принимается ТОЛЬКО после побайтовой
проверки (diff или хеш-сравнение тестовых файлов).

## Правила тестирования полноты истории

**Обязательный алгоритм верификации:** при написании теста полноты загрузки истории агент ОБЯЗАН включить проверку через экспорт + скролл + чтение краёв DOM (см. ARCHITECTURE_STANDARDS.md, секция «Стандарт тестирования полноты истории»).

**Запрещено:** проверять полноту только по логам (oracle=complete reason=..., doneReason='top', historyFullByQuiet=true). Логи — это решение кода, а не доказательство полноты в глазах пользователя.

**Обязательно:** тест полноты должен:
1. Вызвать экспорт (авто или ручной) и получить текст экспортного файла
2. Прокрутить чат до верха (scrollTop=0) и дождаться стабилизации scrollHeight
3. Прочитать первые 3 и последние 3 сообщения из DOM чата (голова и хвост истории)
4. Сравнить с экспортным файлом: экспорт должен содержать ВСЕ сообщения из DOM в правильном порядке (хронологически: user→assistant→user→assistant→...)

**Критерий приёмки теста полноты:**
- `exportedMsgs.length === domMsgs.length` — количество сообщений совпадает
- `exportedMsgs.slice(0, 3) === domFirst3` — первые 3 совпадают (текст + роль)
- `exportedMsgs.slice(-3) === domLast3` — последние 3 совпадают (текст + роль)
- Порядок ролей в экспорте = порядок ролей в DOM (user/assistant чередуются)

**Пример правильной проверки (словесный алгоритм, не псевдокод):**
1. Дождаться события автоэкспорта (auto-export fired) или вызвать ручной экспорт
2. Получить текст экспортного файла (.txt)
3. Спарсить текст в массив сообщений (каждое сообщение: роль + текст)
4. Скролл чата: scrollTop=0, ждать 500мс стабилизации scrollHeight
5. DOM-чтение: querySelectorAll по селекторам сообщений чата, взять первые 3 и последние 3
6. Сравнение: длина массивов + содержимое первых 3 + содержимое последних 3 + порядок ролей

**Реализация хелперов:** агент сам решает, как реализовать вспомогательные функции (получение экспортного файла, чтение DOM) под существующий API проекта. Хелперы должны быть переиспользуемы в других тестах полноты.

## Автовыбор варианта (2026-09-07)
DHS-агент при наличии нескольких вариантов решения НЕ спрашивает пользователя — самостоятельно выбирает вариант, реалистичный и максимально соответствующий мировым стандартам (ARCHITECTURE_STANDARDS.md), объявляет выбор одной строкой с обоснованием и продолжает работу. Исключение — необратимые действия (удаление данных, публикация, смена мажорной версии): там подтверждение обязательно.

## 9. Регрессионный контур
Каждая задача-фикс включает:
- тест на сценарий бага;
- байтово-идентичные тесты на рабочие сценарии;
- список «НЕ трогать» + тест неизменности.
«Готово» принимается только с цитатами: jest + live-прогон ≥2 чатов.

## 10. Анти-закрытие
Не завершать ответ «готово / решено» без закрытия всех пунктов чек-листа.
Стоп-слово пользователя «ЧЕК-ЛИСТ» — немедленная остановка, вывод чек-листа
целиком, признание нарушения.

## Сессии DSH — семантика для промптов (фиксация 2026-09-13)
- **НОВАЯ сессия** = задача выполняется в новой сессии, которую пользователь создаёт в GUI DSH (кнопка «New Session») перед вставкой промпта. В промптах писать: `DSH: workspace ai-context-monitor-clean → работать в НОВОЙ сессии с именем «X»`.
- **ТЕКУЩАЯ сессия** = продолжить работу в уже идущей сессии (упоминать только когда явно нужно продолжение; в промптах по умолчанию — никогда).
- Кодер DSH не умеет создавать сессии инструментами (HTTP 403); создание — только из GUI. Если создание нового чата нужно — пользователь создаёт сам.
- Правило применяется ко всем промптам по умолчанию, кроме случаев явного продолжения.

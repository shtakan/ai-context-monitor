## Конвенции процесса

Правила, выработанные в цикле O-15…O-20:

1. **Два провала фикса одного симптома → следующий промпт только измерение.** Если симптом воспроизводится после второй итерации, следующая сессия заказывает измерение без правок.
2. **Каждое утверждение с основанием.** Все утверждения помечены: «лог строки N», «скриншот», «гипотеза, не проверено».
3. **Критерий приёмки привязан ко времени.** «Снимки в пределах одной секунды» или «одновременно».
4. **Харнесс ≠ приёмка live-багов.** Приёмка = живое побайтовое равенство на захваченном payload в реальном браузере.
5. **Правило R-D (regression + defect-path).** Каждый защитный фикс по дефекту закрывается пинами на КАЖДЫЙ путь записи (base write path) и на единственную точку выхода — а не на «представительный» путь:
   - **D (defect)** — пин на воспроизведение дефекта: точная форма входных данных из живого артефакта (для O-27 — `f.txt` = `)]}'\n[""]\n`) на ВСЕХ путях записи базы (`open`, пагинация, `probe` step/finish, passive `folwr`/`folif`, XHR, DOM-добор) и в единственной точке скачивания (`downloadBlob` → `aiCmAutoExportStartDownload`);
   - **R (regression)** — пин на легитимный вход: база и экспорт байтово прежние (сравнение снимка и байтов файла «до/после» гарда), плюс прогон существующих наборов (O-11/O-31/O-15…O-20) в том же сьюте;
   - плюс пин «диагностика только под гейтом» (`aiCmDebug`) и «байты выхода при гейте вкл/выкл идентичны».
   Живой образец: `tests/gsa-o27-protective-form-guard.test.js` (16 пинов).

6. **Секция CHANGELOG создаётся только в релизном коммите** одновременно с бампом версии (`manifest.json`/`package.json`/`package-lock.json`) и версионными пинами; до релизного решения CHANGELOG не трогается. Страж — `tests/version-hygiene.test.js` (`manifest.version ===` версия ВЕРХНЕЙ записи CHANGELOG).
